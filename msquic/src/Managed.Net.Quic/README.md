# Managed.Net.Quic

This standalone .NET 10 project exposes the copied `System.Net.Quic` API under
the `Managed.Net.Quic` namespace using translated MsQuic, translated PicoTLS,
and the .NET BCL platform/crypto provider.
It does not require a native MsQuic, Schannel, or OpenSSL TLS provider.

From the repository root:

```sh
dotnet build msquic/src/Managed.Net.Quic/Managed.Net.Quic.csproj -c Release
dotnet run --project msquic/tests/ManagedNetQuic -c Release
# Full serial JIT/NativeAOT, IPv4/IPv6, cached/uncached checks:
python msquic/scripts/test-managed-net-quic.py
```

The final postprocessed MsQuic source must already exist in
`msquic/generated/TranslatedMsQuic` (generated by `msquic/scripts/translate.sh`).
The project links that source, `MsQuic.Extensions.cs`, and the BCL host into one
assembly so partial declarations and host callbacks share the same types and
MsQuic globals. There is no need to copy generated files manually. Override
`TranslatedMsQuicDirectory` to use a different final generated directory. Do not
also reference `TranslatedMsQuic` or `MsQuic.BclHost` in this project: that would
create a second copy of the transport types and state.

For a consumer, add a normal project reference and import `Managed.Net.Quic`:

```xml
<ProjectReference Include="path/to/Managed.Net.Quic.csproj" />
```

```csharp
using Managed.Net.Quic;

// QuicConnection, QuicListener, QuicStream, and their options resolve here.
```

For a listener and client exchanging messages in one app, see
[`samples/ManagedNetQuicRoundTrip`](../../samples/ManagedNetQuicRoundTrip/README.md).
The integration checks live in `msquic/tests/ManagedNetQuic`. This integration
targets direct API use; it does not replace the framework's HTTP/3 transport
inside `HttpClient`.

Certificate handling uses public .NET `X509Chain` and `MatchesHostname` APIs.
Custom chain policies, trust stores, revocation settings, extra certificates,
validation callbacks, certificate selection callbacks, and client certificates
remain in the API path. Validation callbacks receive policy errors and can
explicitly approve them, including a missing requested client certificate.
PicoTLS still requires valid CertificateVerify signatures for presented
certificates. Identities use their BCL private-key handles without PKCS12 export.

The current crypto provider supports AES-128/256-GCM, P-256 ECDSA and RSA-PSS
with SHA-256 (RSA keys at least 2048 bits). Cipher policies intersect with the
supported AES suites; a policy with no supported suite is rejected. It does not
add ChaCha20 or other signature algorithms to the existing provider. Certificate
trust/revocation uses the platform services behind .NET X509Chain; hostname
matching uses .NET's portable implementation rather than a native TLS provider's
hostname rules.

TLS secret logging honors `SSLKEYLOGFILE` and the
`System.Net.EnableSslKeyLogging` AppContext switch. The shared host and API
registration live for the process, like the original wrapper's registration;
connections, listeners and streams should be disposed asynchronously.

The sources copied from .NET retain their original MIT license headers.
The existing `System.Net.Quic.DisableConfigurationCache` AppContext switch and
`DOTNET_SYSTEM_NET_QUIC_DISABLE_CONFIGURATION_CACHE` environment variable retain
their names for configuration compatibility.
